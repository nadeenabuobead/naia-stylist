# Verifying the React Router 7.18 CSRF/Origin Behavior on Real Vercel Infrastructure

**Status: a verification plan only. Nothing here has been executed. No live Vercel setting was read, changed, or queried beyond what's already documented as blocked.**

## What's settled vs. what isn't

**Settled, by direct source inspection and a local empirical test** (`app/lib/react-router-7-18-csrf-origin-check.test.ts`):
- react-router@7.18.5's CSRF check compares the browser's `Origin` header against the full origin (scheme included) of whatever URL the server adapter constructs.
- This app's real build takes `@react-router/express`'s `createRequestHandler` path (confirmed: the compiled `build/server/.../index.js` exports no `fetch` property, so `@react-router/serve`'s cli.js falls through to this adapter, not `@remix-run/node-fetch-server`).
- That adapter's URL construction depends on Express's `trust proxy` setting, which `@react-router/serve` never enables and offers no way to enable.
- **This means:** if this app is reached through `@react-router/serve` (i.e. the process started via `npm start`/`docker-start`) behind something that terminates TLS before the Node process sees the connection, a legitimate same-origin mutating request gets rejected.

**NOT settled — this is exactly what staging QA needs to answer:** whether the real, live Vercel deployment path for this project is `@react-router/serve` at all. Vercel's own framework-detection (`"framework": "react-router"` in `vercel.json`) may instead route through `@vercel/react-router`'s native integration with Vercel's own Node.js serverless runtime — a path this repo's code can't fully account for, because `@vercel/react-router`'s own dependencies contain no Express/HTTP-server code (confirmed: only `ts-morph` and `@vercel/static-config`, both build-time). Vercel's own serverless request-handling is platform infrastructure, not something in this repository to read.

## The verification plan (to run during isolated staging QA — not this session)

1. **Deploy this exact branch to an isolated staging URL** (not the shared staging alias — per [[feedback_lane_boundaries_staging]], never manage staging aliases from a feature lane). This is a deployment action requiring separate authorization; not done by this phase.
2. **Send one deliberate, harmless same-origin mutating request** against a real route with an `action` — e.g. a `PUT`/`PATCH` to a low-stakes endpoint, or exercise an existing form submission the UI already has, from a real browser hitting the real HTTPS staging URL. If it succeeds normally, the real Vercel path already handles origin/scheme detection correctly (whether via `@vercel/react-router`'s own runtime or because Vercel's internal topology preserves a signal this repo's code can read) — no further action needed.
3. **If step 2 fails with an unexpected 400 "Bad Request"** that wasn't happening before this upgrade, that is the scheme-mismatch finding manifesting for real, not just locally. At that point, with a live reproduction in hand:
   - Confirm via Vercel's own request logs (dashboard, not this repo) what `X-Forwarded-Proto`/`X-Forwarded-Host` the platform actually sends to the function, and what the function's own `req.protocol`/`req.socket.encrypted` report — this tells you definitively which adapter path is live and whether trust proxy is the missing piece.
   - Only then decide between the two legitimate fixes already identified and NOT applied by this phase: (a) if `@react-router/serve` is confirmed live, add a minimal custom server wrapper that calls `app.set('trust proxy', true)` before handing off to the existing handler — the standard, correct Express configuration for exactly this topology, not a CSRF weakening; or (b) if a different root cause is found, address that specific cause. Adding this app's own domain(s) to `allowedActionOrigins` remains available as a documented option but is explicitly NOT the first move, since it's broader than necessary if the real fix is simply enabling trust proxy correctly.
4. **Also exercise, in the same staging pass:** a genuine cross-origin forged request (confirm it's still correctly rejected — the security property this upgrade exists to provide must demonstrably still work), the Stripe/Shopify webhook endpoints (confirm delivery still succeeds — expected to be unaffected per the no-Origin-header finding, but staging is the place to prove it against real webhook senders, not just the local simulation), and the Clerk/Shopify OAuth callback flows (expected unaffected, GET-only).
5. **Record the result** (which adapter path was confirmed live, whether step 2 passed or needed step 3's fix) back into this document or a follow-up note, so the next person doesn't have to re-derive it.

## Why this wasn't resolved in this session

Querying Vercel's actual runtime behavior requires either a live deployment (explicitly out of scope — "No unified RC changes... deployments") or Vercel dashboard/CLI access to inspect function logs and headers for a real request. The Vercel CLI is reachable via `npx` and authenticated in this environment, but the specific step needed to go further (`vercel link` to a project, to then query logs/env) was blocked by the permission classifier in a prior turn of this engagement, and — per this phase's explicit instruction — was not retried. This verification plan is written so that whoever next has staging deploy authorization can execute it directly, without needing to re-investigate the React Router internals from scratch.
